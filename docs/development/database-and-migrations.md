# Database and Migrations

The local PostgreSQL initialization script receives database names, owners, and passwords through explicit Compose environment mappings. It creates six logical databases with distinct owners and never grants cross-service access.

Files in `/docker-entrypoint-initdb.d` run only when PostgreSQL initializes a new `postgres_data` volume. Changing `.env` later does not update an existing volume. Apply deliberate migrations/role changes for an existing database; do not delete a user's volume automatically. Core owns additive migrations `001_core_vertical_slice.sql` through `006_core_payment_recovery_claims.sql`; Food owns `001_food_vertical_slice.sql` through `005_food_idempotency_eligibility.sql`; Restaurant owns its Alembic revision; Healthcare owns `001_healthcare_booking.sql` and `002_healthcare_slot_reuse.sql`; Ride owns its Alembic revision. The Healthcare second migration removes the legacy global `slot_id` uniqueness and adds a partial unique index for active appointments, preserving cancelled/expired history for slot reuse.

Run `scripts/migrate.ps1 .env.example` or `scripts/migrate.sh .env.example`, then the corresponding seed helper; the first argument is an optional env-file path. Neither script deletes volumes. The PowerShell Food seed writes the UTF-8 SQL payload directly to `psql` so the Vietnamese demo catalog is not corrupted by native-pipeline encoding. Food Compose runs against PostgreSQL when `FOOD_PERSISTENCE=postgres`. Core application tests use an in-memory adapter for speed, while explicit PostgreSQL persistence tests are available through `CORE_TEST_DATABASE_URL`; Healthcare slot-reuse checks use `HEALTHCARE_TEST_DATABASE_URL` when a disposable PostgreSQL target is provided.
